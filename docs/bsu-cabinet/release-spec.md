# Кабинет преподавателя БГУ: полная спецификация скилла

Карточка Vercel Board: **#129**. Статус: спецификация для согласования нарезки на тикеты. Предметные термины — в [словаре](../../bsu-cabinet/GLOSSARY.md). Текущие скиллы описывают тестовый режим до реализации; этот документ задаёт целевое поведение, а не разрешение менять рабочий кабинет.

**Цель:** преподаватель устанавливает комплект у себя, один раз настраивает вход и одной просьбой получает заполненный ИП или карточки и один проверенный отчёт. Программе поручены чтение, расчёт, сравнение и проверка записи; агенту — понимание запроса, выбор разрешённого источника и объяснение реальных блокировок. **Выпуск по этапам: сначала ИП, затем карточки.** Успех измеряется тем, что прочитано с сервера, а не закрытым диалогом или ответом агента.

## Для преподавателя и владельца

- «Подготовь ИП по этому ШТ» означает только чтение. «Заполни мой ИП по этому полному ШТ» в рабочем режиме разрешает добавить недостающее и перенести однозначно сопоставленные плановые значения в свой редактируемый план. Не разрешает удаление, исправление чужих строк, запись отчётной части или отправку на проверку. При сомнении в намерении — черновик. Не просить подтверждения каждой строки. Разрешение ограничено годом, преподавателем, источником, разделом и операциями запроса; не переносится на следующую задачу.
- В разработке — только предпросмотр по умолчанию; владелец проверяет снимок, фактический payload и результат одной разрешённой пробной мутации. В рабочем режиме агент сам читает, считает, сравнивает, выполняет разрешённое и выдаёт один отчёт. Вопрос — один, по неразрешимым данным или полномочиям. Первичная настройка и ручной второй фактор — ввод владельцем, не диалог с моделью. Отправка на проверку **не входит даже в рабочую запись**.
- «Заполни карточки за период» ограничивается преподавателем, строкой ИП, видом, группой или потоком и периодом запроса. Разрешено заполнить весь выбранный диапазон, в том числе будущий. Прошедшие занятия по расписанию считаем состоявшимися без журнала и дополнительного подтверждения, если нет известной отмены или переноса. Галочку ставим только для дат раньше сегодняшней. Лекции потока не размножать по группам.
- Первая версия записи карточек: однозначные личные лабораторные и практические с полными исходниками. Полный скилл распространяется также на лекции, УСР, консультации, проверки и аттестацию, но каждый дополнительный вид получает свою проверку обязательных полей и допускается к записи отдельно. Руководство и прочие годовые работы остаются в ИП; не создавать для них фиктивные пары.
- Решение по масштабу: два уже существующих CLI, локальный браузер, openpyxl, локальные артефакты одного запуска. Не нужны служба, очередь, общий сервер, новый агентный харнесс или подключение телефона. Владелец решает о допуске записи отдельно для каждого сценария после приёмки; сейчас допуск не получен.

В **Advanced** необязательны: явно выбранный ранее сопряжённый телефон, другое написание имени для поиска в расписании, источник расписания и известных исключений, исключения по группам/видам. Доступные данные брать из профиля, ИП и файлов; не заставлять повторять их в настройке. Нет зависимости от приложения преподавателя, его базы или частного журнала. Автоматизация не работает по таймеру: отметки обновляются только в рамках явного запроса на заполнение.

### Виды карточек в полном скилле

| Вид | Что отличает запись | Достаточный источник |
|---|---|---|
| Лекции | Одна запись на поток и слот, без размножения по группам; темы именно лекций | Назначение лектора в ИП и расписании, программа/тематический план лекций |
| Лабораторные, практика/семинары | Отдельные личные назначения по группе или подгруппе; вид сверяется с ИП | Расписание преподавателя и темы соответствующего вида |
| УСР | Собственный график и темы, без дублирования обычных пар | ИП и расписание либо график УСР |
| Консультации | Вид консультации и часы по ИП, отдельная датированная запись | График консультаций с часами и видом; не выводить консультацию из экзамена |
| Проверка работ | Вид работы, дата, группа, число работ и применимая норма | Ведомость или перечень проверки, утверждённая норма; не брать число работ из численности группы |
| Экзамен/зачёт | Вид и форма аттестации, группа/поток, нужные числовые поля; повторная сдача отдельно | Расписание сессии и ведомость/данные по аттестации; проверять допустимые опции формы |

Если для работы нет даты или обязательного числа, правило «Выполнено» ничего не подставляет: неполная запись остаётся в предпросмотре. Группы и нормы не выводятся из продолжительности пары или суммы ИП. Технические поля и селекты — в [карте кабинета](cabinet-map.md); неподтверждённые формы не допускать к записи.

## Контракты реализации (предлагаемые команды, не нынешний CLI)

Один процесс по запросу, без фонового наблюдения. `bsu-browser` владеет соединением с браузером и секретами; `mo-cabinet` читает файлы и сравнивает данные без сети, кроме явного получения публичного индекса/книг расписания. Аргументы файлов — локальные пути. На stdout — один документ JSON, диагностика без значений секретов на stderr. Общая оболочка `{schema: "bsu.<вид>/1", status: "ok|blocked|partial|unknown", data, issues:[{code,source,field,expected,actual,next}]}`. Выход 0 — результат проверен (включая пустой diff), 2 — требуется исправить ввод/выбор до записи, 3 — частично применено или исход неизвестен. Неизвестная версия схемы — отказ. Отчёт пользователю — краткая выборка, не полный JSON с личными данными.

### Вход

`bsu-browser login` на своей сессии: проверить точное HTTPS origin и разрешённый маршрут/ожидаемую форму **до доступа к keyring**, после навигации проверить снова; не выбирать последнюю произвольную вкладку. Без login — локальная видимая форма setup; ввести один раз, записать в нативный keyring, очистить передачу и закрыть временную страницу в `finally` также при ошибке/таймауте. Показывать «сохранено» только после успешной записи, не при нажатии. Без доступного безопасного backend — остановка с инструкцией, без plaintext. Legacy не обязателен и не должен незаметно выбирать другую учётку.

Автоматическое чтение страниц остаётся headless. Если нужно участие владельца, **до запуска запроса SMS** перевести собственную сессию в видимое окно: завершить только собственный headless-процесс, дождаться освобождения профиля, поднять headed с тем же профилем и проверить страницу. Нет экрана — понятный отказ до отправки, без пароля/кода в чате, argv или stdout. Владелец вводит SMS непосредственно на сайте; ждать положительный признак кабинета и совпадение личности, а не просто исчезновение `/Login`. Закрытие окна/истечение срока не создаёт второй запрос. Headless при следующем обычном запуске. Advanced: только явно разрешённый `login --sms adb` с привязанным выбранным serial; в ручном режиме даже discovery запрещён. Не сопрягать устройства автоматически, не подключаться к первому mDNS-адресу, не выдавать код через команду или логи. При отказе Advanced продолжать тот же диалог вручную, если его можно показать без потери; иначе стоп, не пересылать SMS.

### Полный ШТ → дифф → проверенная запись

1. `mo-cabinet workload INPUT.xlsx` → `workload/1`: `{sourceSha,teacher,year,sheet,rows:[{sourceRow,identity,autumn,spring,annual}],controls}`. Каждое значение — `{cell:"'ШТ'!AM14", header:[блок,вид,поле], state:"value|blank|unknown", value:"7/2"}`; числа — точные рациональные строки, численность — неотрицательные целые. Для агрегата сохранять все адреса вкладов. Не делать публичный вывод ФИО из книги.
2. `workload.py`: сначала найти единственный лист и многострочную шапку по тексту, блоку и единицам; переносить подпись объединения только внутри его диапазона, нормализовать пробелы/переносы; известные синонимы — явная таблица. Идентифицировать предмет, семестр, вид, численность и итог; не считать две одинаковые подписи одним столбцом. Открыть книгу с формулами **и** `data_only=True`: пропавший кэш → `unknown`, не вычислять произвольные формулы. Нет обязательного заголовка, неоднозначная колонка, смешанные люди/годы без выбора, неизвестная ненулевая статья — стоп. Пропуск становится нулём только для явно определённого поля полной подтверждённой формы; сохранять исходное состояние. Ноль не терять при сериализации. Для данных, которые портал принимает лишь с меньшей точностью, не округлять молча.
3. `bsu-browser snapshot plan` → `snapshot/1`: `{owner,year,editable,sections,rows:[{key,identity,rawFields,normalizedFields}],totals:{autumn,spring,annual,grand},scopeHash}`. Это новое чтение правильной страницы и выбранного года. Ноль строк допустим только при распознанной полностью загруженной таблице. Извлечь и чужие текущему запросу строки в пределах раздела для контроля неизменности. Для `snapshot card --key K --status N` вернуть все Items категории с полями и хешем; неизвестная структура — стоп, не «пусто». Не использовать текстовый `snapshot` или скриншот как снимок данных.
4. `mo-cabinet plan-diff workload.json snapshot.json` → `diff/1`: `{scope,sourceSha,beforeHash,operations:[{op,identity,key?,before,after,expectedPayload,sources}],totals:[{kind,source,computed,before,after}],blocked}`. Ключ семестровой строки — год, семестр, факультет, специальность, дисциплина, курс, форма; сравнивать справочники по однозначной опции, не первому совпадению подстроки. Годовая строка — год и категория; число — сумма её вкладов. Два неразличимых ключа — конфликт. Поля и итоги проверять независимо: осень + весна + годовые = общий, с отдельной сверкой с контрольными значениями книги и вкладом строк вне запроса. Пустой план → Add только назначенных семестров, в т.ч. одной консультации; годовые — редактировать существующий вид. Совпадение → noop, отличие → edit, лишняя строка → preserve. Полный ШТ с несходящимся итогом не записывать даже частично.
5. `bsu-browser apply diff.json` принимает **типизированные** операции, не произвольный action/JS. Проверяет разрешённый объём, sourceSha/снимок, статус плана и соответствие исходным полям фактического payload, включая три отдельных счётчика. Отчёт `result/1`: `{verified:[{identity,key,before,expected,readBack}],unattempted,uncertain,totals,issues}`. Не включать секреты, лишние поля журнала и скриншоты. Никакого автоматического вызова по факту существования файла diff.

### Что известно о серверной записи и что требуется от исполнителя

- В сохранённом `site-js/PersonalPlan-ur-semestr.js:16–24` Add — уже POST, callback добавляет строку и серверный Key в DOM. В `:36–54` редактирование **сначала** меняет видимый текст, `list_ss` передаётся через `int`, Description потом отдельной строкой; callback пересчитывает DOM. `PersonalPlan.js:94–98`: `int('')` и нечисловое значение становятся 0, десятичная запятая заменяется точкой, применяется `parseFloat`, не целочисленная валидация. Это факт клиентского JS, **не контракт хранения NULL/0 сервером**. `PersonalPlan-ur-all.js:84–92` малая годовая форма посылает `Key,Value` из `.val()` и обновляет текст в callback; не переносить правило семестровой формы на все поля. Эквивалентность пустого и 0 после reload не доказана: сохранять raw + normalized, неизвестное сравнение блокирует, пока не квалифицировано на поле.
- `CardOne.js:187–217` собирает **все строки** `SelKey` в таблице `status`, включая тему, группу, дату, время, часы, ready, dl, примечания и поля категории; reload в callback условный. Форму не заполнять урезанной копией таблицы. Данные существующих строк, в том числе неизвестные пилотному виду, сохранить без потерь или запретить запись. Замена на сервере не независимо подтверждена; проектировать консервативно как полную замену.
- Алгоритм: одно изменение в полёте. До POST перечитать и сравнить нужную область со снимком, учесть уже проверенные изменения запуска. Сначала зафиксировать намерение локально (операция, область, ключ/естественный ключ, before и expected, без секретов). Add и Save — **две** контрольные точки. Ожидать ответ именно соответствующего запроса и проверять прикладной результат; предел ожидания предлагается 15 с. Затем новое серверное чтение с принудительным reload без кэша, ожидать завершения загрузки нужной таблицы и маркеров года/ключа, максимум 15 с. Ни пауза фиксированной длины, ни исчезновение диалога, ни HTTP 200 сами по себе не подтверждают запись. Не начинать следующий POST, пока независимое чтение не доказало точный postcondition и неизменность остальных записей. При Add postcondition — появился ровно один новый ключ и нужная идентичность по доступным полям создания, старые ключи целы; продолжить Save только по этому ключу. При Save — все согласованные поля и ожидаемые промежуточные итоги; в конце — четыре итоговых значения.
- Потерян ответ: одно ограниченное независимое чтение, **никаких повторных POST**. Однозначно доказанный результат отметить восстановленным; при отказе/прерванной цепочке остановить пачку и перечислить уже записанное, даже если строка только создана. Иначе `unknown`; не откатывать удалением. При новом запуске пересчитать diff, привязать частичный Add по сохранённому ключу и исходной области, если доказуемо, иначе вопрос. Если чтение снова не удалось, не превращать это в «не записалось». Конкурентное изменение до сохранения — новый diff, старое разрешение на перезапись не наследовать. Без условной записи на сервере остаётся гонка **между последним чтением и POST**: read-back не гарантирует обнаружения затёртой параллельной строки. Карточки допускать к записи только при подтверждённом исключительном редактировании области либо проверенном серверном контроле версии; иначе только черновик.

### Расписание + ИП + темы → карточки

- `mo-cabinet schedule-index --folder URL` → `index/1 {folderId,observedAt,books:[{id,name,modifiedHint,courseHint,semesterHint,yearHint}]}`. Только указанная публичная папка, без аккаунта, cookie кабинета и загрузки файлов на внешние сервисы. Пустая/изменившаяся разметка, неполный список — `blocked`, не «расписания нет». При загрузке выбранной книги проверить формат XLSX, лимиты размера/распаковки, не исполнять макросы или внешние связи. Отпечаток байтов и содержимое C8/эквивалентной шапки проверять независимо от имени. При нескольких редакциях не брать автоматически последнюю по времени: нужен однозначный год/семестр/курс и признак действующей редакции; иначе показать кандидатов. Новый ID или изменившийся SHA того же ID → новый снимок и diff назначений, не доказанный перенос.
- `mo-cabinet schedule-find index.json --year … --semester … --course … --teacher …` → `slots/1 {bookId,sha,scope,slots:[{assignment,discipline,kind,groups,weekday,localStart,localEnd,phase,bounds,sourceRanges,ambiguities}],issues}`. По объединениям связать день → базовое время → поток/группа/подгруппа → предмет → личное назначение. Учитывать альтернативное время внутри ячейки и даты применимости. Не заполнять пустые ячейки значением ближайшего соседа. Фамилия/инициалы или сокращение дисциплины без уникального соответствия → блок. Метки «четн./нечетн.» не дают даты без календарного якоря; отсутствие метки не всегда означает еженедельность. Вид не выводить из адреса или только из ИП, если есть несколько назначений. Слоты без доказанного соответствия вывести, не применять.
- Даты вычисляет календарь по последней действующей книге **того же года, семестра и курса**: границы периода, день недели, время, фаза. Для более раннего периода отсутствие прежней редакции и истории переносов не блокирует расчёт. При отсутствии известного исключения используй слот действующей редакции в пределах её применимости; явное «с …» ограничивает развёртку назад. Применяй известные переносы и отмены, сохраняй ссылку на выбранный файл/редакцию и источник исключения, не переписывай существующую карточку из-за одного изменения расписания.
- `topics/1 {discipline,edition,lessons:[{kind,ordinal,topic,sourceRef}]}` — темы из программы или тематического плана, отдельно по виду, с исходной страницей/строкой. Отсутствие распределения по занятиям блокирует подстановку темы, но не расчёт дат. Не выводить порядок из одного перечня тем или копировать лекции в лабораторные. Если в подтверждённом журнале есть фактическая тема, она имеет приоритет.
- `mo-cabinet card-diff slots.json snapshot-card.json --plan snapshot-plan.json [--topics topics.json] [--facts facts.json]` → `diff/1`. `facts/1`: `{events:[{assignmentRef,originalSlot,date,time,kind,group,topic,hours,delivery,evidenceRef}],exceptions:[{originalSlot,action,newDate?,newTime?,source}]}`. Журнал, ведомость и известные исключения необязательны: они уточняют событие, а не дают разрешение на обычный расчёт. Отмена исключает экземпляр, перенос меняет его дату/время с сохранением исходного ключа; фазу серии не сдвигать. Если имена, слот или исключения конфликтуют, блокировать затронутые строки.
- **Расчёт «Выполнено».** Один раз зафиксировать `asOfDate` в `Europe/Minsk` и включить его в результат. Для каждой записываемой карточки после учёта известных исключений: `ready = lessonDate < asOfDate`. Сегодня и будущее — `false`, независимо от времени дня. Например, при `asOfDate=2026-09-24` для дат `23.09`, `24.09`, `25.09` результат `true/false/false`; перенос с `23.09` на `25.09` даёт одну карточку с `false`. Не требовать подтверждения на весь период или на каждую пару; в отчёте явно указать, что отметка рассчитана по дате. При изменении даты до записи сравнить ожидаемый дифф заново, не переносить разрешение на изменившиеся поля молча.
- ИП задаёт виды и потолок часов; темы и длительность берутся из своих источников, а не из календарной догадки. Подгруппа в номер + примечание преобразуется только при известном соответствии. Дата ISO в diff, в форме полный год. Сопоставление по строке ИП, виду, группе или потоку и идентичности экземпляра; сравнивать тему и часы отдельно. Точный повтор — noop, тот же экземпляр с другими полями — дифф, если различается только рассчитанная отметка, иначе конфликт. Часы существующих и новых карточек проверять вместе против ИП. `card-plan` разворачивает готовые YAML-данные и не заменяет расчёт. Интеграция с приложением не входит в этот выпуск.

**Два сквозных допуска.** (1) На чистой поддерживаемой ОС с нативным keyring, без adb, legacy, checkout и старого Chrome-профиля, преподаватель устанавливает архив и даёт короткую просьбу с синтетической ШТ; на согласованном тестовом входе лично вводит реквизиты и один SMS. Все ресурсы видимы, в выводе нет секретов, один отчёт. Linux Secret Service/Wayland, Windows Credential Manager, macOS Keychain и поиск браузера OS-зависимы: публиковать список лишь фактически прошедших платформ. (2) Локальный сценарий с полным файлом нагрузки, четырьмя итогами, пустым → заполненным планом и повтором; два сбоя на разных границах, параллельная правка, две редакции расписания, прошлые/сегодняшние/будущие карточки без журнала, известные отмена/перенос и уже существующая карточка. Сравнить фактический payload, серверный журнал чтений/записей, все старые поля, четыре итога, отсутствие удаления/submit и один итоговый отчёт «проверено / не начато / неизвестно». Оба допуска **не выполнены** в рамках этой спецификации.

**Обслуживание и стоп.** При изменении разметки Drive, заголовков XLSX, версии схемы или полей кабинета не подбирать похожее молча: отключить затронутую запись, оставить диагностику с адресом, обновить обезличенный fixture и повторить соответствующий допуск. Локальные снимки и намерения доступны только владельцу; хранить до завершения сверки/разрешения неопределённого исхода, не печатать полную книгу, не добавлять в git. Не обещать восстановление данных или атомарность между двумя POST. Для реальной публикации открыты: полный обезличенный образец ШТ, проверенный независимый read-back и семантика пустых полей, защита от второго редактора карточки, якорь учебного календаря и чистый платформенный запуск. Архив прежних редакций, неизвестные переносы и независимый журнал проведения не являются допуском для расчёта по согласованному правилу даты. Ни один из них не заменяется успешным `--help` или скриншотом.
